# Общий PoC: многоклеточность и Rust/wgpu (WebGPU + WebGL2)

React управляет редактором из 1–40 архетипов, инструментами и камерой. Rust/hecs в Worker рассчитывает жизнь клеток, деление, наследование связей и движение организма. Отдельный Rust/wgpu-модуль рисует мир. Оба набора изменений работают с одним состоянием симуляции.

## Рендеринг

`WorldView.tsx` выбирает бэкенд: `auto` (WebGPU, затем WebGL2), `webgpu` или `webgl`; последние два включаются через `?renderer=webgpu` и `?renderer=webgl`. `RustWorldView.tsx` передаёт снимок через `set_frame(cells, terrain, links)` и камеру/слой/выделение через `set_view`. Rust владеет `requestAnimationFrame` и сам вызывает `render`; JS освобождает ресурсы при размонтировании.

На кадр требуется до четырёх draw call: карта, подписи, связи, клетки. Клетки используют исходный snapshot по 40 байт на инстанс. Для связей Rust сопоставляет ID с координатами за O(N + E), затем загружает по 24 байта на связь: `[ax, ay, bx, by, idA, idB]`. WGSL строит сглаженный отрезок, меняет его цвет и толщину при выборе клетки. Геометрия клеток и связей вычисляется в vertex/fragment shaders; CPU не строит отдельные окружности и треугольники.

GPU-буферы клеток и связей переиспользуются и растут по необходимости. Пустой массив связей убирает старые линии. Некорректные ссылки отклоняются до загрузки в GPU. Подписи один раз растеризуются в Rust (ab_glyph) в атлас-текстуру. Terrain лежит в текстуре 48×48 `Rgba32Float`, а не в storage-буфере: так сцена работает и на WebGL2, где SSBO отсутствуют. Копирование через wasm-bindgen и загрузка в GPU остаются; zero-copy и GPU-симуляция не реализованы.

При работающей симуляции Worker отправляет до 30 снимков в секунду. На паузе новый снимок отправляется после размещения, редактирования, сброса или одного шага. Камера и выделение работают независимо от снимков. Рендерер перерисовывает сцену при изменении данных, вида или размера.

## WebGL2

Это не второй рендерер: тот же `WorldRenderer`, `web.rs` и `scene.wgsl` собираются с feature `webgl` и работают поверх WebGL2. Naga транслирует WGSL в GLSL ES 3.0, а GL-бэкенд wgpu создаёт WebGL2-контекст. Поэтому карта, подписи, связи, выделение и hit testing на обоих бэкендах совпадают.

WebGL2 — это GLES 3.0, поэтому у него нет compute и storage-буферов. Terrain хранится в текстуре `Rgba32Float` и читается через `textureLoad`; лимиты устройства запрашиваются как `Limits::downlevel_webgl2_defaults()` (гарантированные 16 КиБ UBO и 2048 px текстуры). Шейдер использует только возможности ES 3.0: instancing, `fwidth`, `flat`, `discard`.

Выбор бэкенда происходит до создания WebGL/WebGPU-контекста: Rust сначала проверяет `navigator.gpu` и адаптер, и только потом создаёт surface. Если WebGPU уже занял canvas и инициализация не удалась, JS повторяет попытку на новом canvas с принудительным `webgl` — один canvas не может сменить тип контекста. При потере WebGPU-устройства React перемонтирует представление с бэкендом `webgl` и новым canvas.

Для WebGPU нужны localhost или HTTPS и поддержка браузера. Сборка с `webgl` включает `wgpu-core`/`wgpu-hal`, glow и GLSL-бэкенд naga, поэтому wasm заметно больше, чем в WebGPU-only варианте: около 3,4 МБ raw и 1,07 МБ gzip в текущей release-сборке. JS-загрузчик и ABI остаются частью интеграции WASM. Потеря устройства отслеживается через JS `device.lost`: в используемой версии wgpu 24 аналогичный callback освобождает wasm-bindgen Closure раньше завершения Promise. Закрытие рендерера не должно оставлять необработанных Promise-ошибок.

## Геном и совместимость

На обоих бэкендах доступны все три настройки адгезии, запрет деления и пример M1 → связанные M2/M3, затем M3 → связанный M3 и отдельный M1. Физика связей находится только в симуляции. Подробнее: [многоклеточный геном](multicellular-genome.md).

Сохранения редактора записываются в `cellhub.genome.v2`; при отсутствии v2 читается старый `cellhub.genome.v1` с восемью режимами. Старым режимам добавляются разрешённое деление и выключенные связи. Сохранение полного мира пока отсутствует.

## Запуск и проверки

```sh
npm run build:wasm
npm run build:rust-frontend
npm run dev
```

Оба WASM-модуля собираются также через `./start.command` и `npm run build`. Node.js должен быть версии 22.12+ или 24+. Сборщик поддерживает Cargo из `.tools/cargo`, обычную установку и явный `CARGO_HOME`; CLI wasm-bindgen ищется также в `.tools/wasm-bindgen`. PowerShell-обёртка использует тот же сборщик. `CARGO_TARGET_DIR` учитывается при поиске артефактов.

`npm test` запускает 19 Rust-тестов (15 симуляции + 4 подготовки связей), 5 тестов модели редактора и 3 теста настоящего WASM. Они проверяют все сочетания флагов адгезии, одновременное деление соседей, движение пары, смерть/reset, сохранения, ссылки генома и координаты массового размещения.

`npm run test:browser` выполняет сценарий в отдельном Chrome с включённым CDP и Vite dev-сервером. По умолчанию используются `http://127.0.0.1:9224` и `http://127.0.0.1:5175`; их можно изменить переменными `CELLHUB_CDP_URL` и `CELLHUB_URL`. Скрипт предназначен для отдельного тестового профиля: он меняет геном и популяцию в тестовой вкладке.

Браузерная проверка включает цикл M1/M2/M3 (порог деления M3 снижен до 1 для быстрого наблюдения), save/load, выделение, паузу без повторных снимков, один шаг, GPU-пиксели обычной/выделенной/удалённой связи, сброс, узкую раскладку и принудительный WebGL2-бэкенд (`?renderer=webgl`). Headless Chrome на Linux может не включать WebGPU-canvas в скриншот композитора, поэтому тест отдельно читает GPU-текстуру и проверяет цвета; одного отсутствия JS-ошибок недостаточно.

`?count=20000&paused` размещает клетки равномерно внутри карты. Проверены загрузка 20 000 клеток и один шаг; устойчивый FPS и длительная работа 20 000 связанных клеток не измерялись. Для профилирования отдельно измерять шаг Worker, получение и перенос снимка, подготовку связей, CPU submit и GPU/frame time. Время queue.submit не является временем работы GPU.
